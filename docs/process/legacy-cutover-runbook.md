# Cutover legacy — runbook opératoire

Statut : **préparation et répétition uniquement**. Ce runbook décrit le futur cutover ; aucun passage public n'est autorisé par sa seule présence. Le [contrat canonique](../architecture/legacy-migration-v1.md) fixe les mappings et les blocages. La branche de travail est `review` ; `main` exige une promotion distincte validée.

## Préparer le socle (lot courant)

1. Vérifier le SHA parent, `review`, `origin/review`, worktree et le registre des migrations DEV. Le socle initial partait de 49 migrations ; le candidat corrigé en suit 52. Ne jamais modifier 049–051 ni le dossier Streamer.bot vivant.
2. Vérifier le snapshot local ignoré : `npm.cmd run migration:legacy:analyze -- ../local-data/streamerbot-snapshots/20260926T145119069Z` depuis `server/`. Le manifest doit correspondre aux 17 fichiers ; 0 chemin inconnu. Ne jamais committer les JSON privés, un rapport avec logins, des IDs Twitch ou des secrets.
3. Vérifier Prisma et les migrations 050–052 en schéma isolé : `npm.cmd run prisma:generate`, `npx.cmd prisma validate`, `npm.cmd run migration:legacy:verify-ddl`. Contrôler RLS, révocation des droits navigateur, contraintes NATIVE/LEGACY, calendrier Faveur, résultat Giveaway et diff physique.
4. Exécuter la répétition globale privée : `npm.cmd run migration:legacy:rehearse -- ../local-data/streamerbot-snapshots/20260926T145119069Z`. Le script crée un schéma `batch_test_*`, vérifie un plan de purge par table avant mutation, utilise uniquement des identités Twitch synthétiques, provoque un rollback transactionnel, applique chaque domaine, vérifie les invariants puis détruit ce schéma. Répéter sur état privé propre pour comparer le rapport agrégé. Aucun Player public n'est importé.
5. Contrôler la suite pertinente, builds, typechecks, catalogue 120 et les tests TwitchIdentity/Compte. Vérifier le diff complet et l'absence de données privées suivies par Git. Appliquer toute migration additive à DEV seulement après réussite de la validation isolée et contrôle du statut Prisma ; revérifier `_prisma_migrations`, RLS/grants et le catalogue, sans appliquer la migration des Players publics.
6. Publier un commit dédié sur `review` uniquement si le socle est stable et migration-ready pour sa portée. Vérifier GitHub après push. Ne pas promouvoir `main` automatiquement. Les fixtures ne prouvent pas une résolution Twitch réelle.

Contrôle DEV du 27 septembre 2026 : 050–052 appliquées par Prisma, registre à 52 migrations, 16 tables de fondation avec RLS et droits navigateur révoqués, catalogue à 120 personnages, dix Players publics et zéro `MigrationBatch` public. La répétition privée a vérifié l'effacement d'une `PlayerSession` de fixture, le calendrier de 44 états Faveur, le champ de date XP de 45 profils et un résultat Giveaway legacy sans récompense. Le cutover n'a pas été exécuté.

## Préparer le vrai cutover (mission ultérieure)

7. Choisir une fenêtre avec Axel et annoncer l'arrêt des écritures Streamer.bot. Vérifier qu'aucun Concours n'est actif ; sinon attendre sa clôture. Vérifier le jour et le mois `Europe/Paris`, les éditions Event/Code, la bannière et les verrouillages quotidiens. Aucun changement de priorité n'est implicite.
8. Capturer une **nouvelle** copie horodatée et son manifest SHA-256, sans modifier le dossier vivant. Ne pas réutiliser le hash figé de la répétition comme s'il représentait l'état final. Conserver la capture finale locale, ignorée par Git.
9. Exécuter le scanner sur les 17 sources et tous les profils, y compris exclus. Un fichier/champ nouveau, notamment Calendrier de Noël, arrête le cutover jusqu'à classification, mapping et nouvelle répétition. Contrôler la population dérivée des éléments valides ; ne pas imposer 45 au snapshot final.
10. Avec credentials Twitch applicatifs valides et une action explicite de l'opérateur, lancer `npm.cmd run migration:legacy:resolve-identities -- <snapshot-final> ../local-data/identity-resolutions/<nouveau>.json [ids-déjà-vérifiés.json]`. Le rapport détaillé reste local/ignoré. Vérifier login actuel, User ID, display name, renommages, doublons et absences ; aucun scope chat. Une ancienne identité ne se déduit pas d'un pseudo. Rapprocher en lecture seule avec toutes les `TwitchIdentity` existantes et les comptes web ; un conflit bloque.
11. Produire le plan global **avant mutation** : mappings, comptes conservés/créés, profils exclus, corrections/quarantaines, domaines, 0 chemin inconnu, tables et nombres de lignes de purge, FK, soldes et claims. Le rapport partagé reste agrégé. Toute valeur illisible, relation fantôme, compte matché par displayName ou provenance insuffisante bloque.
12. Faire une répétition complète du **snapshot final** en schéma privé, avec les IDs Twitch réellement résolus comme entrée vérifiée et une copie représentative des comptes web. Vérifier l'idempotence sur état propre, le rollback provoqué, les contraintes DB et les invariants : aucune BusinessOperation/ResourceMovement/ItemAcquisition/BossAttack/FriendHeart/reward fictive, aucun double claim, aucun Player fantôme, identité et préférences conservées, `PlayerSession` pré-cutover vidées, `GiveawayWin` legacy sans faux tirage, jours XP et états Faveur cohérents. Une différence avec la capture figée est expliquée par la nouvelle source, jamais ignorée.
13. Préparer une sauvegarde technique temporaire du schéma public et une restauration testée ; elle ne devient pas un historique gameplay permanent (R927). Noter le hash de la capture finale, la version migrateur, le SHA code et la liste des mappings vérifiés. Geler le trafic applicatif et les jobs producteurs pendant l'opération.
14. Exécuter le futur outil de cutover public **uniquement après sa mission d'activation dédiée et sa validation**. La fondation actuelle ne fournit volontairement aucune commande d'application au schéma public. Son ordre contractuel est : vérifier le même hash et les IDs, créer le batch, purger explicitement dans l'ordre FK y compris les `PlayerSession`, préserver comptes/rôles/prefs/privacy, créer/réutiliser Players par Twitch User ID, importer état personnel et domaines partagés, contrôler les compteurs, puis commit. Une erreur avant ouverture entraîne rollback/restauration ; ne jamais ouvrir sur un batch partiel.
15. Contrôler après migration : `_prisma_migrations` (052 incluse), RLS/grants, batch `COMPLETED`, 0 issue `BLOCKER`, 0 chemin inconnu, FK et comptes, Chat/MP, notifications et `PlayerSession` pré-cutover vides, historiques de test absents, compte web non rattaché `elementKey = null`, premières vues player-facing et absence de double gain. Comparer les agrégats au rapport privé, y compris Boss, Event, Codes, Faveur, dates XP et `GiveawayWin`.
16. Faire reconnecter les utilisateurs dont la session pré-cutover a été invalidée. Activer ensuite les entrées UI/Twitch sur les services PostgreSQL selon une mission séparée. Streamer.bot cesse alors d'être source vivante. Observer le premier jour/mois/rotation naturels et faire valider gameplay/visuel par Axel ; distinguer ces tests de la validation technique. Supprimer la sauvegarde temporaire selon la politique opératoire après stabilisation.

## Arrêt et rollback

Un blocage de couverture, identité, catalogue, FK, contrainte, double récompense ou domaine conditionnel arrête le cutover. Avant ouverture, restaurer l'état public sauvegardé et garder Streamer.bot autoritatif ; enregistrer le hash et les erreurs dans un rapport local privé. Après ouverture, ne jamais rejouer le même snapshot sur les Players sans procédure exceptionnelle de maintenance et nouveau plan validé. Aucun `TRUNCATE CASCADE`, force push, suppression de `main`, appel Twitch sans credentials ni écriture dans les JSON vivants.
