## Autorité et mise en service future

La migration additive 061 crée les quatre tables backend-only et la liaison du consentement OAuth à WebIdentity. Elle ne configure aucune autorité et n'importe aucun Player. Elle n'est pas appliquée au schéma public par cette mission. Une future mission approuvée doit d'abord la déployer par Prisma et vérifier le registre, RLS/grants et les indexes ; le nouveau backend ne peut utiliser ces tables avant cette étape. La review indépendante précède toute promotion `main`.

`TWITCH_COMMAND_PILOT_ENABLED` est le hard-off de déploiement. `TWITCH_NATIVE_GLOBAL_ENABLED` est un gate supplémentaire false par défaut ; aucun endpoint de ce lot n'active GLOBAL. `TwitchNativeAuthority.configure` vérifie Player ACTIVE, ADMIN actif, opérateur allowlisté et identité Twitch liée de l'opérateur. Les badges Twitch ne donnent aucun droit. Le singleton PostgreSQL porte désir/révision/opérateur ; les targets portent les IDs numériques et la propriété personnelle. Aucune décision d'autorité n'est gardée uniquement en mémoire.

Le POST existant `/me/twitch/commands/pilot` exige désormais `{ acknowledgement: "STREAMERBOT_PATH_DISABLED", twitchUserIds?: [...] }`. Sans liste, il cible l'opérateur lié ; avec liste explicite, les IDs peuvent précéder tout Player. Une mutation remplace l'ensemble canary, sans abandonner la propriété NATIVE des anciens targets. La case à cocher de Configuration > Compte confirme les chemins Streamer.bot concernés ; ce n'est pas une détection du logiciel externe. DELETE écrit OFF atomiquement ; le prochain EventSub après commit ne passe plus le parser, le métier ou l'outbound, y compris sur une autre instance. Les opérations déjà commitée conservent leurs reçus et réponses ; OFF ne rejoue ni n'annule leur gameplay.

Le status sépare `desiredAuthority`, `effectiveAuthority`, `transportValid`/`authorityUnavailable`. Après reconstruction, une révision active exige une nouvelle preuve ACTIVE du manager : opérateur/broadcaster, receiver numérique, subscription ID et callback exact. Tant qu'elle manque, effectif OFF. Le consentement Runtime demeure chez Twitch ; App Access Token acquis dynamiquement, aucun access token utilisateur Runtime stocké. Les transports Faveur/Gift/Giveaway spécialisés gardent leurs gates existants, sans activation par ces fondations.

## Provisioning et récupération standalone

`PrismaTwitchPlayerStore` exige couverture NATIVE avant toute création. Advisory lock par User ID et verrou partagé du contrôle permettent le recontrôle après attente ; mêmes defaults via `bootstrapPlayer` que le standalone. Le premier message continue dans le pipeline et son receipt protège le replay. Aucune WebIdentity ; login/displayName seulement métadonnées initiales. Sans élément, XP messages bornée au niveau 2, rappel !element au franchissement du seuil une seule fois par opération persistée ; les commandes exigeant un élément gardent leurs propriétaires.

R1046 utilise `/me/twitch/recover/start` authentifié, sans champs d'identité fournis par le client. State distinct `claim_`, hash/nonce/durée, WebIdentity capturée, JWT OIDC signé et validation Twitch/Helix du même ID numérique. L'action explicite est **Récupérer mon profil Twitch**. Même Player déjà lié : idempotent. Le web temporaire accepté a seulement les defaults vides, ses ressources à zéro, Missions initiales sans progression, privacy par défaut et éventuellement Tutoriel/session/présence app inoffensifs. XP, ressources, élément, Box/Teams/items/cosmétique, autre TwitchIdentity, rôle, opérations, relations, état temporel, préférence inconnue ou nouveau domaine FK avec lignes bloquent. Les colonnes physiques inconnues dans les defaults/Player bloquent aussi. Le contrôle conservateur central est `isDisposableWebPlayer` ; un doute n'autorise aucune fusion.

Le même panneau Configuration > Compte est accessible avant le choix permanent d’un élément, afin de garder le web temporaire disposable. Les deux Players sont verrouillés dans l'ordre de leur UUID, la même WebIdentity est déplacée et seul le Player temporaire est nettoyé. Le subject/token Supabase reste valable : le bootstrap résout désormais le vrai Player Twitch. Le callback frontend appelle le pipeline complet de refresh Player/ressources/Box/Team/pity/progression/Faveur et autres domaines chargés, sans logout. Ceo significative doit être traitée par remplacement opérateur, pas par auto-claim.

## Canary ciblé : plan, répétition et apply gardé

Commandes depuis `server/` : `migration:legacy:canary:plan`, `:rehearse`, `:apply`, `:rollback`. Les deux premières sont lecture seule/public pour le plan et mutations exclusivement `batch_test_*` pour la répétition. `apply` et `rollback` sont des CLI locales opérateur ; aucun endpoint HTTP d'application n'est ajouté. Aucun apply public n'a été exécuté dans cette mission.

Le plan/rehearsal prend `--snapshot <dossier-fige-ignore> --identities <rapport-frais-ignore.json> --twitch-id <ID-numerique-verifie> --expected-player <UUID-ou-ABSENT> --cutover-at <ISO>`. Les fichiers doivent déjà exister et être ignorés, sans liens/traversée ; le manifest vérifie exactement les 17 sources et hashes. Le rapport Helix strict/frais doit correspondre au snapshot, sans conflit/doublon. Le login source est trouvé exclusivement via ce rapport, jamais par rapprochement de nom avec PostgreSQL. Le plan partagé imprime seulement hashes, mode/présence cible, domaines, agrégats différés et blockers.

La répétition prépare deux fixtures privées : absence Twitch-only et vrai compte web vérifié synthétique avec gameplay significatif/rôle/préférence préexistants. Elle importe, compare et restaure le préimage ; aucune AuthIdentity réelle ni gameplay public n'est copié.

Une application ultérieure explicitement approuvée exige en plus `--schema public --operator-player <UUID> --confirm-twitch-id <meme-ID> --confirm-hash <SHA-snapshot> --confirm-identity-report-hash <SHA-rapport> --legacy-path-frozen STREAMERBOT_PATH_DISABLED`. Cible/Player attendus exacts, LEGACY, blockers=0 et aucune opération pertinente en cours. Les opérations PENDING, receipts RECEIVED/stage EXECUTING et outbound SENDING/AMBIGUOUS bloquent. Le gel des chemins Streamer.bot est une action opérateur externe réelle, confirmée séparément ; Codex ne l'effectue pas dans ce lot.

L'import transactionnel sauvegarde d'abord les lignes ciblées et l'ancienne target dans `local-data/identity-resolutions/canary-backup-<UUID>.json`, ouverture exclusive et fsync avant la première écriture métier. Le checksum entier lie identité, schema, hashes source et target au graphe de lignes ; un second hash vérifie le préimage gameplay. Les valeurs PostgreSQL restent JSON textuel (BigInt et précision timestamp conservés). Les FK sortantes pertinentes sont analysées avant remplacement ; une référence partagée hors périmètre qui empêcherait une restauration exacte bloque le plan au lieu d'être détruite.

La cible passe MIGRATION_PENDING dans la transaction, l'owner personnel commun remplace le gameplay, puis la comparaison lit les ressources, progression, Banque, Gacha, Box/C6, Teams, objets, Missions/Défi, statistiques, Roue/Daily, Expédition et Faveur. Tout écart annule la transaction. Identités/Auth/Player ID/displayName, rôles, privacy et préférences hors gameplay sont conservés pour EXISTING_VERIFIED_TWITCH ; box.sort est une préférence gameplay intentionnellement remplacée. Twitch-only crée Player/TwitchIdentity, aucune WebIdentity. Les globaux et relations ne sont pas purgés ; Social/Boss/Event/Giveaway/Codes/Banner/Contest présents sont agrégés DEFERRED_CANARY_SHARED_FACT, sans endpoint fantôme ni reward inventée.

Un succès reste LEGACY, journal DATA_IMPORTED avec hashes/provenance ; le migrateur ne transfère pas l'autorité. Après comparaison et validation humaine, l'opérateur désactive réellement les chemins remplacés, confirme l'ACK puis transfère l'ID en CANARY NATIVE. Aucun refresh ultérieur ni batch personnel ne peut réimporter ce Player.

## Rollback ciblé

Une mission de rollback explicitement autorisée commence par OFF, contrôle des opérations/outbound incertains et retour explicite de la propriété personnelle à LEGACY. La CLI `:rollback` exige `--backup <backup-ignore.json> --schema public --operator-player <UUID> --twitch-id <ID> --expected-player <UUID-du-Player-importe> --confirm-twitch-id <ID> --confirm-backup-hash <checksum-entier> --restore-authority LEGACY`. Pour une ancienne absence, l'UUID attendu se lit dans le backup créé ; ABSENT n'est pas l'UUID du Player importé.

Le script valide le checksum complet, la dernière provenance DATA_IMPORTED et la cible avant le retour LEGACY puis restauration. Les lignes personnelles et le Player retrouvent exactement leur préimage ; une absence retrouve l'absence. Les FK réelles empêchent de détruire des données partagées apparues depuis l'import. Le journal canary courant est supprimé pour permettre un retour à l'absence, tandis que l'audit opérateur et le MigrationBatch opérationnel restent : restauration ciblée de gameplay, pas effacement de l'audit ni de tout PostgreSQL. Un hash ou backup d'un autre import ne suffit pas.

`migration:legacy:freeze-population -- <snapshot-historique-R1041-existant> <rapport-historique-existant.json> <nouveau-fichier-ignore.json>` génère seulement la décision locale depuis les preuves existantes. Les noms/IDs restent uniquement dans les fichiers ignorés ; les sorties partagées sont agrégées. Champs inconnus/secrets, doublons, 44e membre ou partition différente des 216 échouent.

Le rehearsal final exige ensemble `--identities <nouveau-rapport-frais> --population <decision-locale> --historical-identities <preuve-R1041> --historical-snapshot <capture-R1041>`, en plus du snapshot/cutoverAt existants. Il exige les mêmes 43 IDs fraîchement revalidés et aucun autre blocker. Les deux quarantaines ne sont ni importées ni owner-discarded, même si une future résolution existe : nouvelle décision nécessaire. Les 171 ne produisent pas de faits différés ; leurs endpoints sont abandonnés et comptés séparément. Un nouveau compte test supplémentaire n'est ni auto-inclus ni automatiquement owner-discarded. Les comptes standalone hors population conservent leur gameplay et identités.

Un membre déjà NATIVE avec DATA_IMPORTED reste dans les 43 mais `personalImport=false` et viewer personnel vide. Ses lignes sont protégées indépendamment d'une liste fournie par le caller, avec parents FK nécessaires. Les relations nouvelles peuvent utiliser son Player ID ; les rows préexistantes sont comparées exactement après les domaines. Une collision sur un global/référentiel nécessaire au préimage protégé bloque la transaction ; aucune fusion/déduction silencieuse. Le futur snapshot exact et les collisions partagées doivent encore être examinés dans la mission batch. Le mode dynamique ISOLATED_FIXTURE demeure un diagnostic, jamais une preuve Twitch ni une certification finale 30/31B.
